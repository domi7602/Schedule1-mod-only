## How to use a file

1. Select a file in the [index](_index.md); load only the relevant system and a specialist workflow if needed.
2. Use class/member names as search terms in the actual repository. Candidate paths such as `GameReferences/decompiled/Assembly-CSharp/` and `ThirdParty/S1API/` must be resolved locally.
3. Record the target game build/backend, dependency identity and the exact declaring type. Prefer a supported wrapper when its installed contract fits the task.
4. For a behavior claim, inspect readable implementation or run a bounded test. For a change, resolve lifecycle, authority and failure outcomes before coding.
5. When evidence disagrees, update the affected reference and its related specialist example together. Retain an honest scope/date, not a blanket “verified” label.

## Hook interpretation

All listed hook points are candidates. Prefix work runs before the original; postfix work runs after it. A postfix can alter a return result when the verified contract permits, but cannot prevent side effects already executed. A finalizer and ownership-aware cleanup may be needed for exceptional exit. A base-class patch does not automatically cover overridden methods, and an exported name does not prove that a native target is patchable.
